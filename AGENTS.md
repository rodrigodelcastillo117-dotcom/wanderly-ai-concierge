# Architecture rules

- Deno uses automatic npm dependency resolution via root `deno.json` so pinned edge-function dependencies can coexist with frontend package versions.
- Flight status and its cron share the structured Google widget mapper in `supabase/functions/_shared/flight-serpapi.ts` so deployment includes the dependency; keep it independently testable and reject mismatched dates so another day's status cannot be presented as current.
- Account deletion authenticates the caller in `delete-account`, cancels external billing, removes owned storage via API, calls service-role-only transactional cleanup, then deletes Auth identity; never accept a caller-supplied user ID, so deletion cannot target someone else.
- Account cleanup enumerates live public base tables with UUID `user_id` and explicitly handles friendships, authorship, invitations and trip dependencies; review new non-user_id identity columns so personal data cannot escape erasure.
- Retroactive schema baselines are idempotent and ordered before their historical dependents; legacy Auth FKs remain on deployed tables but reconstructed application tables use plain user UUIDs to comply with Cloud schema rules.
- The Travel Avatar has one source, `profiles.avatar_url`, written only server-side (`generate-avatar` on choose, `avatar-evolve` on each trip souvenir); clients read it through `useMyAvatar()` so header, menu and DNA card can never disagree. Selfies are never stored; variants and the souvenir-free base image live in the private `avatar-private` bucket and every edit starts from that base so the face cannot drift.
- Imported past trips go through `import_past_trip()` (dedupe by PNR / flight+date / hotel confirmation, `fuente='documento'`, paid amounts in the document's currency); prices are never estimated, an absent price stays null.
- Free-text trips go through `_shared/tripSpec.ts` (interpretar-viaje + local reader in `src/lib/tripSpecLocal.ts`): every written place, cruise leg and return city must end in a stop, a leg, an open question or a user-approved exclusion (`checkCoverage`); nothing is generated while questions are open, the original text is kept in `itinerario_json.consulta`, and cruise legs never carry a price (quoted with the cruise line, never added to the total).
- The booking allowlist rules live in `supabase/functions/_shared/booking/allowlistCore.ts` (no data). The server list (`allowlist.ts`, with `why` notes and the full PSL) never ships to the browser: `vite.clientAllowlist.ts` redirects it to `src/lib/bookingAllowlist.ts`, whose data file is generated by `npx tsx scripts/booking/clientAllowlistGen.ts`; regenerate it after changing `PROVIDERS` (a parity test fails otherwise), since the server re-checks every URL before saving or redirecting.
- Incidents (problems and complaints) are `concierge_requests` rows with `type = 'incidente'`; their state, full log and alert queue live in `incidents`, `incident_events` and `incident_alerts` (migration 20261029080000) and change only through `_shared/incidents.ts` / the `incident_*` RPCs. A case is idempotent by key, never closes without the user's confirmation or a human note, and the `incidentes-vigilante` cron escalates anything without progress, so other modules (flight monitor, AI operator, channel adapters in `_shared/channels/`) must open and update cases through that interface, never by writing the tables.
