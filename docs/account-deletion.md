# Account deletion audit — 2026-10-17

## Live inventory and migration gaps

Inspected all 38 public base tables, their columns, foreign keys, policies and relevant indexes. The deletion routine covers all 26 base tables with UUID `user_id`, plus `profiles.id`, both sides of `friendships`, `trip_journal_entries.author_id`, `trip_collaborators.invited_by`, and `rate_limits.subject`.

Seven live tables had no versioned creation statement: `badges`, `missions`, `user_badges`, `user_missions`, `friendships`, `destination_daily_costs`, and `historical_flight_prices`. Added an idempotent retroactive baseline before their historical dependents, plus missing indexes. `mis_amigos` and `user_autonomy` are views, not missing tables; their definitions are now versioned too.

The baseline preserves existing deployed tables, records and policies. New reconstructions use plain user UUIDs rather than adding prohibited Auth foreign keys to application tables; the existing live legacy Auth cascade constraints are intentionally unchanged. Catalog contents are not exported or seeded by this schema-only baseline. A complete clean-database replay of all older migrations has not been verified.

Applied SQL also exists under `drizzle/migrations`, as generated by the migration tool. Identical SQL is copied to the classic `supabase/migrations` history for repository consumers. These are two representations of the same changes, not two independent deployment pipelines.

## Deletion sequence

1. Verify caller with Auth; reject arbitrary user identifiers and require both confirmations.
2. Cancel a linked Stripe subscription before erasure (fail closed if billing cannot be cancelled).
3. Remove owned Storage objects via API, including ordinary UUID folders and `avatars/<uuid>/`.
4. Run service-role-only transactional public data cleanup: delete the caller's rows, relationships and authored shared journal entries; cascade children of owned trips. Preserve others' trips, profiles and private records, detaching references to deleted trips.
5. Delete the Auth identity last; return success only after this succeeds.
6. Clear local session and query cache, then return to landing.

The public-table cleanup is transactional, but billing, files and Auth are separate services. A late failure may leave a partially erased account; the UI reports this and allows retry. Both SQL routines deny execution to anonymous and authenticated Data API clients.

## Verified

- Two confirmation validation tests pass, including rejection of caller-supplied `user_id`.
- Real disposable-user Profile flow returned HTTP 200 `{"ok":true}`, signed out, and returned to `/`.
- Readback: zero rows across all 26 user_id tables, zero profile/Auth identity, friendship/collaboration/authorship references, owned trip and files.
- Bystander profile, trip, shared journal entry, expense and file remained; their expense reference to the deleted trip became NULL.
- Mobile confirmation and deletion also returned 200 and redirected to landing; both disposable accounts were removed after testing.
- Live unsafe requests returned 401 with invalid authentication and 400 with a supplied target user ID; neither caused deletion.

## Limits

This erases active IATOS application data; it is not a blanket certification of GDPR compliance. Already-delivered emails, provider bookings, payment-provider records, third-party analytics and retained backups/logs require separate retention/erasure procedures. Live Stripe cancellation is untested because this project has no configured paid subscriptions.
